Appendix B — The diagrams as text

Every diagram in this document, written out: a description in words, for screen readers and search, and its source in Mermaid, which GitHub draws and anyone can edit in a pull request. The pictures in the chapters are exported from the editor’s document; these text versions are kept in step with them, and the sync tool reports any picture that has changed since its text version was last checked.

Plaintext exists only on the desktop and inside an approved request

In The design on one page. One account key. The desktop encrypts messages before upload, and each reader or writer opens its own copy. The desktop app reads the sources on the desktop (mail, chats, calendars), makes and keeps the key, encrypts each message and computes search tags. It sends ciphertext and tags, and attachments as they are, to the server. Readers and writers (AI assistants, the web app, second devices and scripts), each with its own token, send a token and request to the server. The server finds the token’s copy, opens the key per request, searches and decrypts hits, returns the results and drops the key afterwards. It stores and looks up ciphertext, search tags, token hashes and locked copies of the key in the database, and stores and reads attachments in the blob store, encrypted under the storage key, which is sent with each request and never kept. The server never stores the account key, a token or plaintext. The blob store sees each attachment in the clear while it handles a request, and keeps only ciphertext.

The account key exists in the clear in only two places

In How it works. Where the account key lives, where only a locked copy lives, and where it never goes. In the clear, the key exists only in the desktop OS keystore, at rest on each approved desktop and made on the first one, and in server memory, with its two derived keys, for one approved request only. Only a locked copy is in the database, one copy per approved token wrapped under a key from it, and in backups, where deleted copies stay until the backup expires, up to 30 days. The AIs, board and scripts hold a token but never the key, and the server unlocks it for them. AI providers see only the results they asked for. Logs and operator staff hold no key, no token and no plaintext. A token opens only its own copy, so deleting that copy cuts its holder off at once.

The account key is born on the desktop, and only a locked copy reaches the server

In How it works. Create. The desktop app generates the account key from 256 random bits and stores it in the OS keystore. It signs in and asks the server for a desktop token, and the server replies with one. The desktop app wraps the account key under a key derived from the token and sends the locked copy to the server, which stores the token’s hash and the copy in the database. The account key never leaves the desktop in the clear.

The account key is unwrapped for one request and never written down

In How it works. Read. A reader or writer sends a request carrying its token. The server looks up the token’s hash in the database and gets back its locked copy. A key derived from the token unwraps the account key, in memory only. The server looks up the query’s tags and gets back ciphertext rows, decrypts the candidates and builds the answer, and returns the results. The request ends and the account key is dropped.

A new holder gets its own copy, made inside the user’s session

In How it works. Update. The user approves a new reader or writer, inside a session that holds the account key. The server makes a new token and wraps the account key under a key derived from it, stores the new token’s hash and the copy in the database, and hands the new token to the reader or writer once. Renewal runs the same steps, then deletes the old token’s hash and copy.

An expired token finds no copy and is refused

In How it works. Expire. The server finds copies past their expiry in the database and deletes each one’s hash and copy. When a reader or writer then sends a request with the expired token, the server refuses it, and the holder must renew or be approved again. The account key itself is rotated before its nonce budget runs out, by re-encrypting or by re-wrapping data keys (questions 2 to 4).

Deleting copies is how access ends

In How it works. Delete. The user revokes a token, or deletes the account. The server deletes that token’s hash and copy, or every copy and row. Backups keep old copies until they expire, up to 30 days. If every holder is lost, the next desktop makes a new account key and collects again.

Messages are encrypted on the desktop before they leave it

In How it works. Collect and push. The desktop app reads a new message from a local source, such as mail, chat or calendar. It encrypts the message under the account key and computes its search tags. It sends the ciphertext and tags to the server over TLS, with its token. The server stores them and cannot read them. The message is searchable as soon as it is stored.

Approving a reader or writer creates one token and one copy of the account key

In How it works. Approve a reader or writer. The user approves it by OAuth consent, by the web app opened from the desktop, or with a matching code. Inside the user’s session, the server makes a token and a copy of the account key locked under it, stores the token’s hash and the copy in the database, and hands the token to the reader or writer once.

The account key is unlocked for one request and dropped when it ends

In How it works. Search and retrieve. A reader or writer sends a query with its token. The server finds the token’s copy by its hash, unlocks the account key for this request and turns the query into tags. It finds the candidates in the index and gets back candidate rows, still ciphertext. It decrypts only the candidates, checks the real match, and returns the results. The request ends and the account key is dropped.

A writer’s change is encrypted on the server and seen on the next read

In How it works. Update. A reader or writer sends a change with its token, such as an AI tool call or a web-app edit. The server unlocks the account key, encrypts the change, recomputes its tags and stores it. On any reader’s next request, the server returns the updated message.

Revoking deletes a copy, and recovery needs another approved device

In How it works. Revoke and recover. The user revokes a token, or a lost desktop, and the server deletes its hash and its copy in the database. A new desktop asks the server to join, the user approves the new desktop, and the server gives the new desktop its own token, which opens its own copy of the account key. If every holder is lost, the mirror cannot be read, and a new desktop makes a new account key and collects again from the sources.

Encryption adds well under a second, and the answer lands inside the 10-second budget

In Latency budget. Question to first response is 7.4 seconds at the 95th percentile, of which the mirror is 0.405 seconds. These are targets, not measurements. The AI provider reads the question and calls the mirror in an assumed 3 seconds. The mirror then takes 0.405 seconds of its 1-second budget: 0.2 seconds for the request to the server and back over the network, 0.005 seconds on the server to find the token and unlock the key, 0.1 seconds in the database to look up the query’s tags, and 0.1 seconds on the server to decrypt and check 200 candidates. The AI provider then writes the first words from the results in an assumed 4 seconds, so the first response arrives at 7.4 seconds, inside the 10-second budget.

Keys isolate stored data either way, and separate instances contain a breach

In Appendix A. Single or multi-tenant. Each user’s key stays on their desktop in both designs, and colours mark whose key locks which rows. With one shared database, users A, B and C, holding keys A, B and C, all use one shared server, which opens key A, B or C inside each user’s request, and one shared database with row-level security, where user A’s rows are locked under key A, user B’s under key B and user C’s under key C. A server breach sees every active user’s requests. There is one system to run, and metadata is visible to the operator. With one instance per user, user A uses server A, which holds key A only, and database A, which holds user A’s rows under key A, and the same for users B and C. A server breach sees one user’s requests. There is one system per user to run and pay for.
